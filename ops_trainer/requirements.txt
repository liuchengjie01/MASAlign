# Pinned by running opd_masalign's unit tests (19, including the --vlm
# encode-path tests) + end-to-end CPU smoke tests on a compute node (not the
# login node -- see slurm/setup_and_test_cpu.slurm) with tiny instruct
# models: text-only (full hand-off schema + the MINIMAL 4-required-field
# contract, docs/DATA_FORMAT.md) and --vlm (HuggingFaceTB/SmolVLM-256M-
# Instruct on real screenshots from a collaborator's rollout dump). All unit
# tests pass and all training loops complete with finite loss/gradients.
# Verified pure-Python/torch versions only -- NOT yet verified on GPU or
# with a real 9B model (that needs the 8xA100 run). If you hit a
# GPU-specific issue, torch/transformers/accelerate versions are the first
# things to reconsider; everything else here is hardware-agnostic.
#
# transformers>=4.46 is the floor for --vlm (Idefics3ForConditionalGeneration
# / SmolVLM didn't exist before), but pinned to 5.0.0 because a real
# collaborator VLM (AutoGLM-Phone-9B, architecture "glm4v") needs much more
# than that floor -- three separate issues, only the first two of which are
# fixed by a newer transformers version at all:
#   1. glm4v's config/processor classes weren't registered before ~4.53 --
#      on an older version AutoProcessor doesn't error, it silently falls
#      back to a bare tokenizer (this is why opd_trainer.py hard-checks
#      `hasattr(processor, "tokenizer")` right after loading one).
#   2. glm4v's published config uses the newer `rope_parameters` key
#      (confirmed via HF's config.json for zai-org/AutoGLM-Phone-9B); 4.57.1's
#      Glm4vTextConfig still only reads the older `rope_scaling` key, so
#      `self.rope_scaling` silently stays None and crashes deep in attention
#      (`self.rope_scaling["mrope_section"]`). 5.0.0 reads `rope_parameters`.
#   3. opd_trainer.py loads the model via AutoModelForImageTextToText, not
#      the older AutoModelForVision2Seq -- glm4v is registered ONLY in the
#      newer class's model mapping. This one was a real code bug (fixed),
#      not a transformers-version problem, at any version of transformers.
# All three were verified end-to-end against the real 9B checkpoint on a
# real GPU (forward + backward, finite loss and gradients) before pinning
# to 5.0.0, not inferred from documentation.
#
